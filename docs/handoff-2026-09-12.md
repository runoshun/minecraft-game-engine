# Handoff: Vanilla-first Portable DSL / Fabric retirement work

Date: 2026-09-12

## 1. Executive summary

The project direction is **TypeScript `portableDsl` -> versioned Portable IR -> generated vanilla datapack as the primary deployment path**. The Fabric runtime is transitional compatibility/development infrastructure and is intended to be deleted after the remaining retirement gates are closed.

Portable v5 / the full 40-brick Breakout gate is committed at `15e8cf3` and passed mod-free E2E. The current uncommitted milestone is **Portable IR / DSL v6**, which adds the bounded pinball primitives from ADR 0014:

- static `segment` / `capsule` collision against dynamic circles;
- AABB `trigger` / `whenTriggered` center-point sensors;
- two-pose `flipper` declarations selected by an ordinary portable condition;
- a complete `examples/portable-pinball-core` acceptance game.

The v6 pinball prototype has passed the functional mod-free E2E gate on `second`: segment/capsule rails, trigger drain, circle bumpers, real A/D flipper input, Space launch, fixed camera, HUD, Display projection, sound and particles all worked on Minecraft 26.1 with `loader=vanilla`, `mods=[]`, and no installed runtime JAR. **ADR 0013 retirement gates 1 and 2 are therefore green.**

Fabric is still not removable. Gate 3 (required UI/input/presentation scope), gate 4 (generated ownership/reload/cleanup), and gate 5 (removing arbitrary runtime TypeScript/Fabric-host dependency) remain open. Repeated pinball load/restart testing exposed a concrete gate-4 issue: persisted Display/camera entities in unloaded chunks can temporarily duplicate until their chunks are loaded and cleanup runs.

## 4. Portable v6 semantics

### Segment and capsule

`game.segment(id, { ax, ay, bx, by })` is a zero-radius static capsule. `game.capsule(id, { ax, ay, bx, by, radius })` is a static thick segment. A dynamic `game.circle(...)` may collide with either through `game.whenColliding(...)` in either argument order.

Endpoints are compile-time numeric logic coordinates. The compiler quantizes collision coordinates to approximately 0.01 units and uses bounded scoreboard-safe arithmetic: coarse expanded-AABB rejection followed by endpoint/dot/cross-product tests. This is deterministic arcade collision, not a rigid-body solver.

### Trigger

`game.trigger(id, boxSpec)` declares an AABB sensor. `game.whenTriggered(trigger, watched, ...)` observes the watched circle/box **center point**. It has no implicit physical response; the callback owns score, life, state, sound, etc.

### Flipper

`game.flipper(id, { pivotX, pivotY, length, radius, restAngle, activeAngle, activeWhen })` is DSL sugar for two compile-time capsule poses. `activeWhen` selects which pose is used by collision. It does not simulate angular velocity. Visual articulation is currently represented with separate conditionally visible projections, while the game callback authors velocity/impulse response.

### Explicitly still out of scope

Dynamic segment endpoints, continuously rotating collision geometry, swept collision, 3D collision, restitution/friction solvers, runtime dynamic collections, generic randomness/event dispatch, and Minecraft block/entity hitbox queries are not portable v6 features.

## 7. Lifecycle issue found during v6 E2E

Repeated load/server-restart testing revealed that generated Display/camera entities can survive in **unloaded chunks**. A later `load` kills entities by selector before summoning replacements, but selectors cannot remove entities in an unloaded chunk; once that chunk loads, both the persisted entity and its replacement can coexist. Loading the relevant chunks and running `portable/cleanup` removes the leftovers.

Treat this as a real gate-4 blocker, not merely an E2E artifact. Before Fabric deletion, generated ownership/reload semantics must prevent or deterministically recover from this state without relying on a human to forceload chunks.

## 10. Priority order from here

Proceed in this order unless a new blocker changes the dependency graph:

1. Finish v6 docs/tests/build/cleanup and commit the pinball milestone.
2. **P1 presentation:** define the smallest portable replacement for the required `render` / `actors` semantics. Do not clone the old Fabric API wholesale. Prefer semantic portable declarations and explicitly retire unused compatibility features.
3. **P2 world projection:** add bounded portable equivalents for the world-mutation behavior actually needed by retained games (`setBlock` / bounded set/fill semantics).
4. **P3 UI/input:** decide which sidebar/menu/action-event capabilities remain product requirements, then give those explicit vanilla mappings; mark the rest out of scope.
5. **P4 lifecycle:** harden generated ownership/reload/cleanup, including unloaded chunks and exact controller cleanup, until gate 4 is independently green.
6. **P5 migrate retained examples:** move `topdown-roguelike`, JRPG, or other examples that are meant to survive onto portable semantics and eliminate arbitrary runtime callbacks/Fabric-host calls.
7. Delete Fabric/GraalJS/Mixins and compatibility host APIs only after gates 3-5 are actually closed.
