## 4. Portable v6 semantics

### Segment and capsule

`game.segment(id, { ax, ay, bx, by })` is a zero-radius static capsule. `game.capsule(id, { ax, ay, bx, by, radius })` is a static thick segment. A dynamic `game.circle(...)` may collide with either through `game.whenColliding(...)` in either argument order.

Endpoints are compile-time numeric logic coordinates. The compiler quantizes collision coordinates to approximately 0.01 units and uses bounded scoreboard-safe arithmetic: coarse expanded-AABB rejection followed by endpoint/dot/cross-product tests. This is deterministic arcade collision, not a rigid-body solver.

### Trigger

`game.trigger(id, boxSpec)` declares an AABB sensor. `game.whenTriggered(trigger, watched, ...)` observes the watched circle/box **center point**. It has no implicit physical response; the callback owns score, life, state, sound, etc.

### Flipper

`game.flipper(id, { pivotX, pivotY, length, radius, restAngle, activeAngle, activeWhen })` is DSL sugar for two compile-time capsule poses. `activeWhen` selects which pose is used by collision. It does not simulate angular velocity. Visual articulation is currently represented with separate conditionally visible projections, while the game callback authors velocity/impulse response.

### Explicitly still out of scope

Dynamic segment endpoints, continuously rotating collision geometry, swept collision, 3D collision, restitution/friction solvers, runtime dynamic collections, generic randomness/event dispatch, and Minecraft block/entity hitbox queries are not portable v6 features.

## 7. Lifecycle issue found during v6 E2E

Repeated load/server-restart testing revealed that generated Display/camera entities can survive in **unloaded chunks**. A later `load` kills entities by selector before summoning replacements, but selectors cannot remove entities in an unloaded chunk; once that chunk loads, both the persisted entity and its replacement can coexist. Loading the relevant chunks and running `portable/cleanup` removes the leftovers.

Treat this as a real gate-4 blocker, not merely an E2E artifact. Before Fabric deletion, generated ownership/reload semantics must prevent or deterministically recover from this state without relying on a human to forceload chunks.

## 14. P2 world projection v8 — complete

ADR 0016 adds bounded declarative terrain projection. `game.worldBatch(...)` declares compile-time integer block writes and `game.worldFill(...)` expands an inclusive cuboid at build time. The total portable program is limited to 32 batches / 32,768 writes. Unconditional batches run once on load; `when` batches run while an ordinary portable state/input comparison is true.

The vanilla compiler emits one function per batch, groups writes by chunk, force-loads one target chunk around its `setblock` commands, and immediately removes that force-load before continuing. `portable/cleanup` does not restore terrain. The Fabric compatibility adapter maps the same declaration to existing `world.setBlocks`.

`examples/portable-world-core` is the acceptance source: load builds a small black/white board at x=180..184, A paints its left cells red, D paints its right cells green, and Space restores the surface to white.

Mod-free E2E on `second` passed. After load, the footprint contained 25 black base blocks and 15 white surface blocks. Real-client A changed the left six surface cells to red; real-client D changed the right six to lime while preserving the center column; real-client Space restored all 15 surface cells to white. The generated spectator camera/HUD rendered correctly. No force-loaded chunks remained after batch execution. Teardown ran `portable/cleanup`, explicitly cleared x=180..184/y=89..90/z=0..4, removed the datapack, and verified zero objectives, zero owned title/camera entities, zero controller tags, zero force-loaded chunks, and an all-air 50-block test footprint.

This is intentionally not a general TypeScript world-edit compiler. The existing top-down roguelike creates its 29 x 37 topology from runtime arrays, loops, and seeded randomness; v8 does not make that generator portable. Rewriting retained runtime generation/control flow remains P5 / ADR 0013 gate 5 work.


## 15. P3 UI/input v9 — complete

ADR 0017 closes the design portion of ADR 0013 gate 3. Portable v9 adds one bounded `game.sidebar(...)` with a static title and 1..15 stable rows whose text is composed from literal/state/input tokens. The vanilla backend owns a deterministic auxiliary scoreboard objective, hides row numbers, refreshes row display names after portable state rules each tick, and removes the objective during `portable/cleanup`. Because vanilla's sidebar display slot is global, v9 keeps the existing single-controller deployment contract rather than pretending to provide Fabric's packet-local per-player panel semantics.

Input action edges do not receive a second event API. Retained games should build rising edges from the existing held-input registers plus a previous-value state register. The v9 acceptance example uses W/S selection and a Space rising edge that increments a confirmation counter exactly once while Space remains held. Generic `menu.open/onAction` click bridging and generic `input.pressed` attack/use/swap/drop packet events are explicitly out of scope; retained menus must migrate to bounded state-driven selection plus sidebar/actionbar/world-text presentation.

Acceptance source: `examples/portable-ui-core`. Mod-free E2E on `second` passed. The first render exposed an implementation bug: fake row holders named with a leading `#` are hidden from the vanilla sidebar, so the compiler now emits visible row holder names and uses custom display names for their text. The real 26.1 client then rendered the four rows under `PORTABLE UI V9`. S changed `#selection` to 1000 and the rendered row to `SELECT 1`; W returned it to 0 / `SELECT 0`. Holding Space for about 1.2 seconds increased `#confirms` from 0 to 1000 exactly once, proving the previous-value edge recipe does not repeat every tick; after release, a second Space press increased it to 2000 and the sidebar rendered `CONFIRMS 2`. `portable/cleanup` removed both the sidebar and main objectives, the generated pack was deleted, and the final reload reported no problems and no remaining objectives. ADR 0013 gate 3 is green. P4 lifecycle was subsequently completed by portable v10 / ADR 0018.

## 16. Datapack transfer workflow

Generated datapacks should now be handed from `devcontainer-mcp` to `mc-mcp` by URL rather than copying base64 into tool arguments. The verified flow is: compile the pack under `build/portable/<name>`, create a `tar.gz` with the datapack contents at the archive root, compute its SHA-256, publish that file with the devcontainer file-sharing capability, and immediately call the mc-mcp datapack writer with `archive_url` plus `replace_under=<pack-name>`. Mint a new URL for every deployment because the published links are short-lived and can return 404 after expiry/revocation. A `portable_ui` smoke test transferred 1,635 archive bytes / 14 files successfully and mc-mcp reported the same SHA-256 as the local archive. Use base64 only as a fallback.

## 17. P4 lifecycle v10 — complete

ADR 0018 introduces an optional v10 `ownership` rectangle for entity-heavy generated scenes. The region is limited to 64 chunks, stays force-loaded while the pack is active, and gates ordinary tick logic behind `#ready`. Load schedules `owned_init` two ticks later; that initializer kills the stable namespace owner tag, recreates every declared persistent entity with both owner and resource tags, then marks the game ready. Dynamic X/Z entity writes are clamped to the declared rectangle. Cleanup cancels pending initialization, kills the namespace owner tag, removes the force-load, and removes generated objectives.

The vanilla camera no longer tags a controller or changes it to Spectator. A real-client probe established that an Adventure-mode player can be teleported to a fixed camera position every tick while Minecraft 26.1 still reports held input predicates. Breakout then passed the same mapping: the Camera client stayed at `(88, ~112.02, -22)` in Adventure, A changed `paddleX` from 0 to -4480, and `tag Camera list` reported no tags. This eliminates the offline-controller cleanup debt exposed during v7 acceptance.

The current v10 Breakout pack declares x=80..96 / z=-24..4 ownership, which corresponds to six force-loaded chunks. Delayed initialization produces exactly 48 owner-tagged persistent entities. Two consecutive `/reload` cycles each returned to `#ready=1` and exactly 48 owners, never 96. Cleanup-to-zero acceptance passed: after `portable/cleanup`, the owner count was 0, `forceload query` reported none, and all generated objectives were absent; deleting the pack and reloading left the same zero-residue state. Pinball, presentation, and world acceptance sources all compile successfully as portable v10 with ownership regions. The full Java test suite and `./gradlew build` both pass. ADR 0013 gate 4 is therefore green; the next retirement blocker is gate 5 / P5 retained-example migration away from arbitrary runtime TypeScript and Fabric host capabilities.
